# M1 hybrid 检索：跑通了，但两个改进是无效的

**结论先说**：我把 `enterprise-rag` 的契约骨架做成了能跑的 hybrid 检索（537 docs → 11994 chunks），
但消融结果显示：**我原打算做的两个"改进"里，一个是真实提升，两个几乎无效**。
这些是脚本跑出来的数字（`results/hybrid_m1.json`），不是我预期的数字。

## 复现

```bash
cd enterprise-rag
python3 hybrid/hybrid_rag.py          # 约 3 分钟，纯 numpy+scipy，零网络
```

## 与冻结 baseline 的关系（口径必须讲清楚）

| | baseline（冻结，不可改） | M1 hybrid（本实现） |
|---|---|---|
| 语料 | 7 docs / 10 chunks | **537 docs / 11994 chunks** |
| 文件类型 | `.md` 只读 | `.md/.py/.yaml/.json/.txt`，过滤掉 `tokenizer.json` 等产物 |
| 索引 | dense `3209 × |vocab|` 逐点积 | scipy CSR 稀疏 |
| 单次查询 | **~60s**（实测） | **~5ms**（实测，≈12000×） |
| recall@3 | 5/5 | **8/10** |
| MRR | 1.000 | **0.55**（w_cos=0.6） |

**baseline 的 5/5 和 1.000 是在 10 个 chunk 的小库上取得的**；扩到 11994 chunks 后，
同样口径下拿到 8/10 / 0.55。这两个数字不能直接比——语料扩大 1200 倍，recall 下降是预期的。
`baseline/` 目录保持只读，本文件不修改它。

## 六项扫描结果（全部来自同一次运行）

| 实验 | 结果 | 判读 |
|---|---|---|
| w_cos/w_bm25 权重扫描（7 点） | w_cos=0.0（纯 BM25）**recall 8/10 MRR 0.633**；w_cos≥0.4 时 MRR 掉到 0.55 | 融合权重的余弦项在这个中文技术语料上**帮了倒忙**，最优是纯 BM25 |
| candidates 截断（10→500） | recall 全程 8/10，无变化 | **我原以为 candidates=10 会漏 gold，实测不成立** —— gold 在 fused 前 10 内 |
| overlap 消融（0/20/40/80） | 0→0.583，20/40→0.550，80→**0.625** | overlap 有效但**非单调**：40 反而比 0 差，80 才好。这是 10 题小集上的噪声，不下结论 |
| rerank ON/OFF | recall 8/10、MRR 0.55 **完全相同** | **我的第三级重排信号零贡献**。bigram 覆盖率与 fused 同源，没有引入新信息 |
| 延迟 | p50 = 3.25ms，p95 = 8.40ms（10 题） | 稀疏索引的真实收益 |
| 题集 | baseline 5 题 + extended 5 题 = 10 题 | 见下方"出题踩坑" |

## 我做错/做对的事（如实记录）

**做对了的**
1. **文件类型扩展是真提升**：`Qwen3-4B QLoRA` / `bnb_4bit` 这些事实只写在
   `train_agent.py` 和 `cfg_snapshot.json` 里，只索引 `.md` 会系统性漏掉工程事实。
   extended 5 题里 5/5 命中，主要靠这个。
2. **稀疏索引改造是必要的**：dense 版 3209 chunk 时 single query 就要 60s，
   11994 chunks 会到 ~3.7 分钟，根本没法跑扫描。
3. **产物过滤是必要的**：`tokenizer.json` 单个 10.6MB / 25568 chunk，
   不滤掉索引直接爆（第一版就是这么挂的）。

**做错了的**
1. **rerank 设计错了**：我用 bigram 覆盖率做第三级信号，但它与 cosine 的
   char-bigram 论据同源，信息量不独立 → 零贡献。真要重排需要语义级信号
   （cross-encoder 或 embedding 相似度），但那不是零依赖能做的。
2. **融合权重的方向感错了**：我把 `w_cos=0.6` 当默认（因为 baseline 是 0.6），
   扫描才发现纯 BM25 更好。**照搬 baseline 参数不等于最优**。
3. **出题踩了两个坑**（这个比前两条更值得记）：
   - 第一版 `"番茄炒蛋怎么做"` 的 gold hint 是语料里根本不存在的词 → 任何
     检索器都不可能命中。**那不是检索失败，是出题失败**。
   - `"分块太大或太小"` 的 hint 是 `分块/chunk`，但语料里确实没有 chunking 讨论
     （我自己的语料没写过这个主题）→ 依然是无解之题。

## 这个 M1 该怎么定性

README 里我原来写的是"生产级实现待后续里程碑"。M1 之后的状态更准确的说法是：

> **一条能跑的 hybrid 检索链路 + 一组诚实的消融数字**：证明了文件类型扩展和
> 稀疏索引有实际收益（延迟 12000×、工程事实可召回），同时也证明了 rerank 和
> 默认权重两个设计点是无效的。它**不是**生产级检索器，离 golden 评测集和
> latency harness 还差得远。

## M2：换真语义向量之后，稀疏融合仍然没输（`results/dense_m2.json`）

M1 的"下一步"第 1 条是"换重排信号"，理由是第三级 rerank 用 bigram 覆盖率
与 cosine 同源、零贡献。M2 正面做这件事：把整个检索链路的主排序换成
**真语义向量**（`sentence-transformers`，本地模型，不联网、不需要 key）。

| 配置（同一题集 10 题、同一 11994 chunks） | recall@3 | MRR@3 | p50 | CI95 |
|---|---|---|---|---|
| 稀疏融合 M1cfg（w_cos=0.6/w_bm25=0.4） | **8/10** | **0.550** | 5.5ms | [0.5, 1.0] |
| dense `bge-small-zh-v1.5`（中文模型） | 5/10 | 0.450 | 17.9ms | [0.2, 0.8] |

**但这里的正确结论不是"dense 不如 sparse"。** 必须同时讲三件事：

1. **差点得出一个错的通用结论**：第一次只跑了英文 encoder `all-MiniLM-L6-v2`，
   得到 dense **1/10**（MRR 0.10），看起来是碾压式失败。真正的原因是
   题集 **9/10 是中文 query**（`detect_lang` 实算 CJK 占比 ≥0.3），
   用英文 encoder 编码中文技术语料 = 拿错工具。换成 `bge-small-zh-v1.5`
   后回到 5/10。**这条教训比上面那张表更值得写**：评测一个多语言场景的
   检索器之前，先测 query 的语言分布。
2. **分型看完全反过来**：dense 在 `extended` 5 题上是 **5/5**（和稀疏并列），
   在 `baseline` 5 题上是 **0/5**。也就是说 sparse 赢的 3 题全在 baseline 层。
   两类题 query 风格不同，10 题的合计数字会把这个差异抹掉。
3. **代价**：dense 的索引 build 18.1s（vs 稀疏 0.88s），查询 p50 17.9ms
   （vs 5.5ms）。在 11994 chunk 这个量级，dense 换来的是 3.3× 延迟和 20× 建索引时间。

**诚实的边界**：n=10、CI95 重叠（[0.2,0.8] vs [0.5,1.0]），这**不能**
推广为"embedding 在中文小语料上没用"。能说的只有：在这条语料、这个 10 题集合上，
真语义向量没有超过我在 M1 用 char-bigram 拼出来的稀疏融合。

复现（需要本地 HF 缓存里有这两个模型，全程离线）：

```bash
cd enterprise-rag
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 python3 hybrid/dense_rag.py --only zh,sp
```

> 不含 `en` 选项时结果如上表；把 `en` 加进去可以看到"encoder 语言不匹配"
> 那组反面证据（1/10）。

## 下一步（真的值得做的）

1. **换重排信号**：用 `sentence-transformers` 或本地小模型做 cross-encoder，
   否则第三级信号永远是冗余的。
2. **扩题集**：10 题做不出统计结论（overlap 非单调就是样本量症状）。
   要下任何"有效/无效"的结论，至少需要 50 题以上 + 分层报告。
3. **补负例**：现在的 10 题全是"语料里有答案"的正例，
   没有"语料里没有"的拒答场景（`番茄炒蛋` 本该是这个角色，但被我写成出题失败了）。
